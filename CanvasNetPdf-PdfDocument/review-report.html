CanvasNet Formal Review Report - CanvasNetPdf-PdfDocument

Review that CanvasNetPdf PdfDocument Implementation is Correct

1. Introduction

1.1 Purpose

This document records the formal review of a set of project files.

1.2 Scope

This review covers the PdfDocument software unit of the CanvasNetPdf system — a brand-new, from-scratch PDF tokenizer/parser/content-stream interpreter/renderer delivered across 42 commits on branch feature/pdf-document-support. It is the sole direct unit of CanvasNetPdf and has never previously been formally reviewed. The review covers file-structure parsing (tokenizer, object model, xref, page tree), content-stream interpretation (graphics state, path ops), device color, the filter pipeline (LZW/ASCII85/ASCIIHex/RunLength/CCITT G4), image and form XObjects, font resolution (Type0/Type1/Type1C/Type3/ToUnicode/fallback), sampled functions, shading and tiling patterns, and text rendering (including this session’s new stroke/ fill+stroke render-mode support). Because this unit parses untrusted/adversarial PDF byte streams, the review places particular emphasis on bounds-checking discipline, integer-overflow safety, and whether malformed/adversarial input paths fail closed with a specific typed exception.

Scope caveat (reported separately as a Critical finding, see §3.1): two files that are part of the same PdfDocument unit and implement requirements inside docs/reqstream/canvas-net-pdf/pdf-document.yaml — src/DemaConsulting.CanvasNet.Pdf/PdfDocument.Encryption.cs and src/DemaConsulting.CanvasNet.Pdf/PdfDocument.Fonts.Type3.cs (plus their test files PdfDocumentEncryptionTests.cs and PdfDocumentSymbolicEncodingTests.cs) — are not listed in the CanvasNetPdf-PdfDocument review-set’s paths: in .reviewmark.yaml, confirmed via dotnet reviewmark --elaborate CanvasNetPdf-PdfDocument and dotnet reviewmark --plan --enforce (which lists both source files as globally uncovered by any review-set). They were reviewed anyway, per explicit task instruction, to give complete coverage; findings for them are included below but they are not covered by this review-set’s cryptographic fingerprint and therefore remain formally “uncovered” until .reviewmark.yaml is corrected.

3. Conclusion

3.1 Summary of Findings

# Check Finding
F0 REQIMP-01 (Critical — process/config) .reviewmark.yaml’s CanvasNetPdf-PdfDocument review-set omits src/DemaConsulting.CanvasNet.Pdf/PdfDocument.Encryption.cs, src/DemaConsulting.CanvasNet.Pdf/PdfDocument.Fonts.Type3.cs, and their test files (PdfDocumentEncryptionTests.cs, PdfDocumentSymbolicEncodingTests.cs), despite the requirements they implement being inside the reviewed pdf-document.yaml. Confirmed authoritatively via dotnet reviewmark --plan docs/code_review_plan/generated/plan.md --enforce, which reports both source files as globally uncovered by any review-set in the repository (alongside docs/reqstream/quality.yaml, src/DemaConsulting.CanvasNet/Fonts/CffStandardEncoding.cs, temptest/Program.cs, and two CanvasNet.Tests files — a broader repo-wide coverage gap, not unique to this review). Recommendation: add the four missing paths to the CanvasNetPdf-PdfDocument entry in .reviewmark.yaml.
F1 LOGIC-02/ERR-01/SEC-01 (Critical) PdfDocument.Xref.cs (ParseXrefStreamSection, ~lines 221-284): /W width-triplet values are cast from attacker-controlled PDF numbers with no non-negativity validation. A crafted /W [-1000000 2 1] xref stream drives a negative buffer offset into ReadBigEndian, throwing an unhandled IndexOutOfRangeException instead of the documented InvalidDataException; the constructor’s exception handling does not catch this type, so Open crashes outright rather than falling back to linear scan. No test exists for this input.
F2 LOGIC-02/SEC-01 (High) PdfDocument.PageTree.cs (TraversePageTree, ~lines 61-100): cycle rejection only triggers on a repeated object number; there is no maximum recursion-depth limit (unlike the Form XObject interpreter’s documented hard limit of 12). A page tree built from thousands of distinct single-child nodes recurses unbounded and can trigger an uncatchable StackOverflowException. PdfDocument.ObjectModel.cs’s mutually recursive array/dictionary parsers have the same unbounded-recursion gap (Medium confidence/severity).
F3 LOGIC-02/SEC-01 (High) PdfDocument.Functions.cs (SampledFunction.ReadSample/ReadBits, ~lines 121-153): sampleGroupIndex * outputCount is computed in 32-bit int arithmetic before widening to long. A malformed /FunctionType 0 function with a large (individually legal) /Size and multi-output /Range overflows to a large negative bit offset, bypassing the length guard and throwing IndexOutOfRangeException instead of InvalidDataException. Reproduced by static trace (sampleGroupIndex=600000000, outputCount=4 → negative bitOffset). No test covers this.
F4 LOGIC-02/SEC-01 (High, memory/DoS) Color/filter/image area (per dedicated sub-review): unbounded /Width×/Height (and CCITT /Columns//Rows) allocation enabling memory-exhaustion DoS; an unhandled DivideByZeroException in the PNG predictor for a malformed /Columns//Colors combination; unbounded LZW output growth (decompression-bomb class); unchecked double→int casts from PDF numbers; int overflow in /Hival-based palette-length checks; a raw IndexOutOfRangeException leaking from image pixel decoding on truncated streams. All violate the documented “fail closed with a typed exception” contract for this area.
F5 LOGIC-02/SEC-01 (Medium) PdfDocument.Fonts.Type0.cs (ResolveCompositeWidths, ~lines 391-404): the /W array’s cFirst cLast w range form has no upper bound on cLast - firstCid; a malformed /W [0 2147483647 500] entry drives an unbounded dictionary-population loop — a resource-exhaustion vector, not memory-unsafe, but untested.
F6 ERR-01/SEC-01 (Medium) PdfDocument.Encryption.cs (~lines 259-260, 544, 563, 675): the encryption dictionary’s /Length field is used to derive keyLengthBytes with no range validation before slicing a 16-byte MD5 digest; malformed /Length values throw an unhandled ArgumentOutOfRangeException or DivideByZeroException instead of the file’s otherwise-consistent InvalidDataException convention. A related, lower-severity issue: Aes.Key is assigned outside the try/catch(CryptographicException) block in DecryptAesCbc (~line 978), so an invalid key size throws an uncaught CryptographicException.
F7 LOGIC-01/Medium (content-stream area) PdfDocument.GraphicsState.cs/PdfDocument.PathOps.cs: numeric operands for cm, w, M, and path-construction operators are not checked for finiteness (NaN/Infinity); a crafted huge-digit-run token can produce double.PositiveInfinity, poisoning the CTM or MiterLimit silently rather than failing closed, inconsistent with the finite-check already applied to dash-array entries elsewhere in the same file. Unbounded content-stream operand-stack and q-stack growth (no cap) are related, lower-severity findings in the same area.
F8 READ-07/REQDOC-02 (Low-Medium, documentation-only) Two stale/self-contradicting doc comments found: (a) NamespaceDoc.cs and a test’s XmlDoc still describe Render as rendering no content (“Phase 1” blank-only behavior), contradicted by the fully-implemented content-stream interpreter; (b) PdfDocument.Fonts.cs’s StandardGlyphNames remarks claim unrecognized /Differences glyph names throw InvalidDataException, contradicting the actual (and correctly designed) lenient no-op behavior in ApplyDifferences and that same method’s own correct remarks. Neither is a behavioral defect — both are misleading comments that should be corrected for maintainability.
F9 SEC-03 (Low, informational) Encryption area: password/MAC comparisons use non-constant-time Span.SequenceEqual (low real-world risk for a local-file reader with no timing oracle); derived key material is not explicitly zeroed after use (standard managed-crypto limitation). Recorded for completeness, not blocking.

3.2 Overall Outcome

Overall Outcome: Fail

This review finds the PdfDocument unit to be an impressively thorough, well-tested, and largely spec-correct implementation — requirements traceability is excellent (all 60 requirements map to credible implementations and genuinely-assertive, passing, non-disabled tests), the cryptographic algorithms are independently verified correct, and the newest-landed feature (Tr stroke/fill+stroke render modes) is rigorously tested at the pixel level. However, the overall outcome is Fail because:

  1. A Critical review-set configuration gap (F0) means two in-unit source files implementing seven requirements (encryption and Type3 fonts) are not formally covered by this or any review-set — a .reviewmark.yaml fix is required before this unit’s coverage claim is accurate.
  2. Multiple Critical/High confirmed boundary-condition and integer-overflow defects (F1-F6) allow malformed/adversarial PDF input to crash the process with an undocumented, untyped exception (or exhaust memory/stack) rather than failing closed with the class’s own documented InvalidDataException/ UnsupportedImageFeatureException conventions — a direct violation of this project’s own stated untrusted-input-parser standard, and of the design documentation’s own “Error Handling” guarantees. None of these are exploitable for code execution or key recovery, but all are reachable denial-of-service-class defects against a library whose entire purpose is processing untrusted files.

Conditions required before this review can be considered approved:

  • Correct the .reviewmark.yaml CanvasNetPdf-PdfDocument path list to include PdfDocument.Encryption.cs, PdfDocument.Fonts.Type3.cs, and their test files (F0).
  • Add explicit non-negativity/overflow/upper-bound validation and ensure a typed InvalidDataException is thrown for: xref-stream /W//Index fields (F1), sampled-function bit-offset arithmetic (F3), image/CCITT dimensions and LZW output growth and the PNG predictor divide (F4), composite-font /W CID-range width loops (F5), and the encryption /Length field (F6). Add a recursion-depth guard to page-tree traversal and object-model array/dictionary parsing consistent with the existing MaxFormNestingDepth/MaxType3NestingDepth pattern (F2). Add regression tests for each.
  • Correct the two misleading/stale documentation comments (F8).

No source code or documentation was modified as part of this review; all findings are reported for the orchestrator/maintainers to triage and remediate.
