6. Code Quality, Error Handling, and Security (CODE / LOGIC / ERR / SEC)

Outcome: Fail. Two Critical and one High finding remain or were newly identified; these are untrusted-input-parser robustness gaps consistent with the unit’s fail-closed design goal, not regressions introduced by the documentation-sync pass (which did not touch this code).

New / Still-Open Critical Findings

  • G1 (Critical) — src/DemaConsulting.CanvasNet.Pdf/PdfDocument.Images.cs:367-389: CCITT Group 4 fax decoding allocates its output buffer (sized from /Columns×/Rows) before validating those dimensions are within a sane bound (the bound check runs later, at line ~389, after the allocation at ~line 374). A crafted /Columns//Rows pair can therefore (a) trigger an unbounded-memory-allocation DoS before any check fires, or (b) overflow during the size computation, surfacing a raw OverflowException instead of a typed exception. Confidence: High (direct code read). Fix: move the dimension bound-check (matching the one already applied to ordinary image XObjects at Images.cs:284-288) to before the buffer allocation, and perform the multiplication in checked context.

  • G6 (Critical) — src/DemaConsulting.CanvasNet.Pdf/PdfDocument.Xref.cs:653-672 (ZlibDecompress, the FlateDecode filter implementation): has no cap on decompressed output size. FlateDecode is the single most commonly used PDF stream filter (content streams, object streams, most image data); a small crafted FlateDecode stream can decompress to an effectively unbounded size in memory (a textbook “decompression bomb”), with no typed-exception circuit breaker, unlike the LZW decoder which now has a 64 MiB cap (fixed per Finding 5 above). Confidence: High. Fix: apply an analogous output-size cap (e.g. 64–128 MiB, consistent with the LZW cap) to ZlibDecompress, throwing InvalidDataException when exceeded.

New High Finding

  • G0 (High) — src/DemaConsulting.CanvasNet.Pdf/PdfDocument.Xref.cs, GetObject/ LoadCompressedObject (~lines 489-534): GetObject(number) only populates _objectCache after it finishes resolving. A crafted xref stream where a compressed-object entry’s container-stream number resolves back to itself (directly, N→N, or via a longer A→B→A chain) causes unbounded mutual recursion between GetObject and LoadCompressedObject, with no cycle or depth guard — unlike the page-tree traversal (fixed, Finding 2 above) and Form-XObject/Type3/color-space/ function recursion limits that exist elsewhere in this same codebase (MaxFormNestingDepth, MaxType3NestingDepth, MaxColorSpaceRecursionDepth, MaxFunctionRecursionDepth, MaxPageTreeNestingDepth). This risks an uncatchable StackOverflowException that terminates the host process — the same severity class as the page-tree bug this re-review was specifically asked to confirm fixed, but present in a sibling resolution path that was not covered by that fix. Confidence: High (static trace; not reproduced live, consistent with the conservative-execution posture used elsewhere in this review, since triggering it would crash the process uncontrollably). Fix: add an “in-progress” HashSet<int> of object numbers currently being resolved inside GetObject, mirroring the page-tree visited set pattern — throw InvalidDataException("Object stream contains a compressed-object reference cycle.") on re-entry, add/remove via try/finally. Add a regression test with a self-referential compressed-object xref entry.

Carried-Forward Medium Findings (unaddressed by the documentation-sync pass)

  • (= prior #11, Medium) Non-finite (NaN/Infinity) numeric operands are not validated for cm and path-construction operators (GraphicsState.cs/PathOps.cs RequireNumbers), while the sibling d (dash-pattern) operator and Patterns.Tiling.cs already validate finiteness — an inconsistently-applied fix pattern. Reproduced: a 400-digit content-stream numeral parses via double.TryParse to PositiveInfinity without error and folds into the CTM. Fix: add double.IsFinite validation inside the shared RequireNumbers helper (used by cm, m/l/c/v/y/re, w, M), throwing InvalidDataException.
  • (= prior #12, Medium) No bound on q/Q graphics-state-stack depth or per-operator operand-stack size (ContentStream.cs/GraphicsState.cs), unlike every other nesting/recursion vector in this codebase (Form XObjects, Type3, color-space, function, page-tree — all capped). Fix: add a MaxGraphicsStateDepth constant analogous to the existing nesting-depth constants, checked in OpPushGraphicsState.
  • G10 (Medium, new) — src/DemaConsulting.CanvasNet.Pdf/PdfDocument.Fonts.ToUnicode.cs:226: the bfrange single-destination-array loop has the same unbounded-CID-range-span DoS pattern that was just fixed for Type0 /W (Finding 8 above), but the fix was not applied here. Fix: add an analogous MaxToUnicodeBfRangeSpan bound + InvalidDataException, mirroring MaxCompositeWidthRangeSpan.
  • G11 (Medium, new) — src/DemaConsulting.CanvasNet.Pdf/PdfDocument.Filters.RunLength.cs: RunLengthDecode has no output-size cap, unlike LZW (64 MiB cap) and (once fixed) the recommended FlateDecode cap. Lower severity than LZW/Flate since RunLength’s worst-case expansion ratio is far smaller (≈127:1 vs. effectively unbounded), but still an inconsistently-applied control. Fix: apply the same output-size cap pattern used for LZW.

Low Findings (carried forward, unaddressed)

  • Non-constant-time password/MAC byte-array comparisons (SequenceEqual, not CryptographicOperations.FixedTimeEquals) and no explicit key-material zeroing in PdfDocument.Encryption.cs. Real-world risk remains Low (local file reader, not a network-exposed oracle).
  • Misleading StandardGlyphNames XmlDoc remarks (Fonts.cs:640-645) describing stricter behavior than the actual (correct) lenient fallback.
  • Stale “Phase 1 — blank-only Render” XmlDoc claim in NamespaceDoc.cs:21-28.
  • GetIntEntry/Color.cs helpers used for /Columns//Rows lack their own range validation, which is what allows Finding G1’s CCITT allocation-before-check gap to be reachable in the first place (noted as contributing cause, not a separate defect).

10. Overall Outcome

FAIL.

The documentation-sync pass was executed accurately and in good faith: every specific documentation claim made by the user was independently verified true (with one partial exception — F0’s test-file coverage gap), requirements traceability is now complete (0 orphaned/unsatisfied for this unit), and roughly two-thirds of the prior review’s code-level findings were also fixed with proper regression-test coverage in the same window. This represents substantial, verifiable progress.

However, the unit still does not meet the bar for a Pass:

  1. Finding F0 (review-set scope) remains open: PdfDocumentEncryptionTests.cs and PdfDocumentSymbolicEncodingTests.cs are still outside .reviewmark.yaml’s file list for this review-set, so their 20+ security-sensitive test methods are not formally subject to review enforcement.
  2. Two Critical and one High code-quality finding remain or were newly identified in this pass (G1 CCITT allocation-ordering, G6 FlateDecode decompression-bomb, G0 object-stream self-reference stack overflow) — all in the same “untrusted input must fail closed with a typed exception” category this review-set exists to enforce, and all independently reproducible/traceable via static code analysis.
  3. Several Medium-severity DoS/robustness gaps remain (non-finite operands, unbounded graphics-state stack, ToUnicode bfrange span, RunLength output size).

Required Remediation for a Future Pass

  • Fix G1 (reorder CCITT bounds check before allocation) and G6 (cap FlateDecode output) — both Critical.
  • Fix G0 (add cycle guard to GetObject/LoadCompressedObject) — High.
  • Add .reviewmark.yaml entries for PdfDocumentEncryptionTests.cs and PdfDocumentSymbolicEncodingTests.cs (F0).
  • Address the four open Medium findings (#11, #12, G10, G11) or provide an explicit, documented risk-acceptance rationale for each.
  • Recommended but not blocking: fix the Low-severity documentation/traceability items (G2, G3, G7, G8, G9) and the three carried-forward Low findings.
