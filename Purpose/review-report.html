3. Conclusion

3.1 Summary of Findings

# Status Check Finding
F1 Open (unchanged) DOC-01 High confidence. docs/user_guide/introduction.md, in the PdfDocument.Render(int, int, int) Exceptions list (around line 1242), still states: "UnsupportedImageFeatureException: Thrown for a well-formed but unsupported color space, stream filter, Form XObject, font subtype (/Type0//Type1//MMType1//Type3), ..." — implying /Type0, /Type1, and /Type3 fonts are all unsupported. This contradicts: (a) the implementation (src/DemaConsulting.CanvasNet.Pdf/PdfDocument.Fonts.cs's ResolveFont/dispatch, which resolves TrueType/Type1 → BuildResolvedSimpleFont, Type0 → BuildResolvedCompositeFont, Type3 → BuildResolvedType3Font, and throws only for any other subtype, e.g. MMType1); and (b) the same document's own preceding "Documented scope boundaries" sentence (just above, around line 1125), which correctly lists only /MMType1 fonts (among font-related items) as out of scope. Confirmed via git show bc86abc -- docs/user_guide/introduction.md that this specific line was not touched by the sync pass, even though the pass's own commit message claims font-subtype "unsupported" claims were corrected. Recommendation: Change the Exceptions bullet to read "font subtype (/MMType1)" (or otherwise state that only /MMType1 remains unsupported among simple/composite/procedural font subtypes), matching the surrounding prose.
F2 Resolved USE-02 Fonts.SystemFontCatalog now has a complete ### SystemFontCatalog API Reference subsection in the User Guide (Fonts, FindBestMatch, LoadBundledFallback, SystemFontInfo all documented), added in commit bc86abc. No further action needed.
F3 Resolved USE-02 TrueTypeFont's IsBold/IsItalic/IsFixedPitch properties and GetNameInfo()/FontNameInfo record are now listed in the User Guide's TrueTypeFont code block and prose, added in commit bc86abc. No further action needed.
F4 Open (unchanged) — Observation — Medium confidence. README.md's "📄 PDF Document" feature bullet still does not mention password-protected/encrypted-PDF support, even though PdfDocument.Open(..., string? password = null) is public API and the User Guide documents RC4/AES-128/AES-256 decryption in detail. Not a contradiction, but a completeness gap for a substantial, headline-worthy capability. Recommendation: Add a short clause to the README's PDF feature bullet, e.g. "... and transparently opens common password-protected documents."
F5 Open (unchanged) — Observation — Low confidence. PDF rendering still has no dedicated numbered "Example" in the User Guide's Examples section (Examples 1-13 cover every other major feature), only the brief inline snippet inside the PdfDocument API Reference subsection. Recommendation: Consider adding "Example 14: Rendering a PDF Page" for parity.
F6 New DOC-02 / USE-02 High confidence. TilePaint (src/DemaConsulting.CanvasNet/Drawing/TilePaint.cs) is a public sealed class (constructor, Surface/Transform/XStep/YStep properties, WithTransform), and PathFiller (src/DemaConsulting.CanvasNet/Drawing/PathFiller.cs) has a public Fill(Surface, Path, TilePaint, FillRule, float) overload — the tiling-pattern analogue of the already-documented Gradient overload. Commit bc86abc added a brand-new "🧱 Tile Paint" bullet to README.md's Features list advertising this capability, and its own commit message claims to "document the Fill(Surface, Path, TilePaint, FillRule, float) overload" — but that documentation was added only to the design docs (docs/design/...), not to the User Guide. A full-text search of docs/user_guide/introduction.md for "Tile"/"TilePaint" finds zero matches outside of unrelated PDF tiling-pattern prose; there is no ### TilePaint API Reference subsection, and the #### PathFiller Methods subsection lists only the solid-color and Gradient overloads, omitting the TilePaint overload entirely. A reader following the User Guide alone has no way to discover or use this now README-advertised feature. Recommendation: Add a ### TilePaint API Reference subsection (constructor, properties, WithTransform) and document the third PathFiller.Fill(Surface, Path, TilePaint, FillRule, float) overload in #### PathFiller Methods, mirroring the existing Gradient treatment.
F7 New — Observation — Low confidence. README.md's "📄 PDF Document" feature bullet says rendering covers "... TrueType text ..." only, which undersells the capability: the User Guide (and implementation) show PdfDocument.Render actually supports TrueType, Type1, Type0 (composite/CID), and Type3 (procedure-painted) font subtypes, plus Symbol/ZapfDingbats fallback. This is a wording simplification rather than a contradiction, but it is incomplete relative to what the User Guide itself documents in depth. Recommendation: Consider broadening the wording to "... and text using any of the PDF simple/composite/procedural font subtypes it supports (substituting a matching system or bundled fallback font when none is embedded)," or similar.

3.2 Overall Outcome

Overall Outcome: Fail

Two of the three prior Fail-driving findings (F2, F3) are confirmed resolved by commit bc86abc. However, the review-set still Fails:

  • F1 persists unchanged — the exact same self-contradictory, verifiably-wrong PdfDocument.Render font-subtype exceptions claim identified in the first review is still present, untouched by the sync pass.
  • F6 is a new instance of the same defect pattern as F2/F3 — a public, README-advertised headline feature (TilePaint, introduced in this very sync pass) has zero User Guide API documentation, exactly the coherence gap this review-set exists to catch. Notably, the sync commit's own message claims to have documented the TilePaint Fill overload, but did so only in the design docs — not in the (in-scope) User Guide.

Findings F4, F5, and F7 remain lower-severity observations that do not independently drive the Fail outcome but are recorded for completeness.

Required follow-up before this review-set can be considered Pass/approved:

  1. Correct the PdfDocument.Render Exceptions entry in the User Guide so only /MMType1 is listed as an unsupported font subtype, matching the surrounding prose and the implementation (F1).
  2. Add a TilePaint API Reference subsection and document PathFiller's TilePaint Fill overload in the User Guide (F6).
  3. Optionally address F4, F5, and F7 for completeness/parity.

No code or documentation was modified by this review; all findings are reported here for the orchestrator/maintainers to action.
